# 로그인 세션과 일반 로그아웃

## 로그인과 토큰 검증
- 로그인·가입 완료마다 새로운 UUID `sid`를 발급한다. 해당 접근·리프레시 토큰과 `refresh_token.session_id`가 같은 값을 가진다.
- 같은 계정의 다른 로그인은 서로 다른 `sid`를 가진다. 물리적 기기 지문이 아니라 로그인 시 발급한 쿠키로 현재 로그인을 구분한다.
- `POST /api/auth/refresh`는 기존 리프레시 토큰의 해시·서명·만료·회원·계정 버전과 `sid`를 검사한다. 접근 토큰을 재발급해도 같은 `sid`를 유지한다.
- 접근 토큰을 사용하는 보호된 API는 같은 회원의 로그인 기록이 존재하고 만료되지 않았는지 매 요청 검사한다. 삭제·만료·잘못된 `sid`·다른 회원의 `sid`는 `401 UNAUTHORIZED`다.
- 접근 토큰의 유효기간은 최대 1시간이며 로그인 기록의 14일 만료 시각을 넘지 않는다. 재발급 응답 `expiresIn`은 실제 남은 유효시간이다.

## 로그아웃 요청
`POST /api/auth/logout`. 요청 본문과 접근 토큰은 필요하지 않다. 기존 `refreshToken` 쿠키와 `GET /api/auth/csrf`에서 받은 `XSRF-TOKEN` 쿠키·`X-XSRF-TOKEN` 헤더를 함께 보낸다.

- 전달된 리프레시 토큰의 해시와 일치하는 로그인 기록만 삭제한다. 이후 해당 `sid`로 발급·재발급된 접근 토큰과 리프레시 토큰은 즉시 거절한다.
- 다른 로그인 기록과 계정·프로필·서류·소셜 연결은 그대로 유지한다. 탈퇴 신청 시 모든 기록을 삭제하는 처리는 별개다.
- 성공은 `200 {"message":"로그아웃되었습니다."}`, `Cache-Control: no-store`이며 기존 속성의 `refreshToken` 쿠키를 `Max-Age=0`으로 제거한다.
- CSRF가 유효하면 쿠키 누락·이미 삭제됨·만료된 토큰도 기존과 같이 200이다. 로그인 기록을 특정할 수 없는 요청으로 다른 로그인을 삭제하지 않는다.
- 만료된 Bearer 헤더가 있어도 쿠키 기반 로그아웃은 처리한다. CSRF 오류는 403, DB 삭제 실패는 500이며 실패 시 쿠키를 지우지 않는다.
- 로그아웃 성공 전에 인증 검사를 마치고 실행 중인 요청까지 취소하지는 않는다. 동시에 재발급된 접근 토큰도 로그아웃 이후에는 삭제된 `sid`를 사용할 수 없다.
- 프론트는 성공 후 현재 기기의 접근 토큰을 제거하고 로그인 화면으로 이동한다. 서비스 이용을 재개하려면 소셜 로그인을 진행한다.

## 마이그레이션
- Flyway V39는 기존 `refresh_token` 테이블에 고유한 `session_id`를 추가한다. 새 테이블이나 기존 계정·서류·소셜 연결 삭제는 없다.
- 기존 행에는 서로 다른 UUID를 채우지만 이미 서명된 토큰에 `sid`를 추가할 수는 없다. 새 서버는 `sid` 없는 토큰을 허용하지 않으므로 기존 로그인은 배포 후 한 번 재로그인이 필요하다.
- 이전 서버는 세션 검사를 하지 않으므로 새 정책 적용 시 이전 서버 인스턴스가 요청을 계속 처리하지 않도록 배포한다. 운영 마이그레이션·배포 결과는 코드 및 CI 검증과 별도로 확인한다.
