# Git Workflow

이 문서는 HIRELINK Backend의 Git 협업 흐름을 맞추기 위한 기본 제안입니다. 아래 세부 규칙은 팀 합의에 따라 조정할 수 있으며, 아직 확정된 팀 규칙을 의미하지 않습니다.

## 1. Issue 생성

1. 작업 성격에 맞게 Feature, Fix, Other 템플릿 중 하나를 선택합니다.
2. 작업 목적과 완료 조건을 `Description`과 `Tasks`에 작성합니다.
3. 이슈 번호를 확인한 뒤 해당 번호를 브랜치와 PR에 연결합니다.

하나의 이슈는 한 가지 목적과 검토 가능한 크기로 나누는 방식을 권장합니다.

## 2. Branch 생성

최신 `main`에서 작업 브랜치를 생성하는 방식을 기본안으로 제안합니다.

| 작업 유형 | 형식 | 예시 |
| --- | --- | --- |
| 기능 개발 | `feat/#이슈번호-기능명` | `feat/#12-job-posting` |
| 버그 수정 | `fix/#이슈번호-수정명` | `fix/#18-refresh-token` |
| 리팩터링 | `refactor/#이슈번호-작업명` | `refactor/#21-auth-service` |
| 환경 설정·기타 | `chore/#이슈번호-작업명` | `chore/#7-ci-config` |

- 작업명은 짧고 의미가 드러나는 영문 소문자와 하이픈 조합을 권장합니다.
- 한 브랜치에는 가능하면 하나의 이슈만 포함합니다.
- 긴 작업에서는 `main`의 최신 변경을 주기적으로 반영하되, rebase 또는 merge 방식은 팀이 합의해 사용합니다.

## 3. 개발

1. 이슈의 범위 안에서 구현합니다.
2. Controller, Service, Repository 등 기존 패키지 구조와 책임을 따릅니다.
3. 동작 변경에는 가능한 범위에서 테스트를 함께 작성하거나 보완합니다.
4. API 계약이나 실행 방법이 바뀌면 관련 문서도 함께 갱신합니다.

## 4. Commit

커밋 메시지는 [Commit Message Convention](./commit-message.md)을 따릅니다.

- 검토 가능한 단위로 나누어 커밋하는 방식을 권장합니다.
- 비밀키, 개인 환경설정, 빌드 산출물은 커밋하지 않습니다.
- 커밋 전 변경 파일과 테스트 결과를 확인합니다.

## 5. Pull Request 생성

1. 작업 브랜치를 원격 저장소에 push합니다.
2. `main`을 대상으로 PR을 생성합니다.
3. PR 템플릿의 작업 내용, 체크리스트, 관련 이슈, 리뷰 요청 사항을 작성합니다.
4. 관련 이슈에는 `closes #이슈번호`처럼 GitHub의 종료 키워드를 사용할 수 있습니다.
5. 테스트하지 못한 항목이나 후속 작업이 있다면 PR 본문에 명시합니다.

PR 크기는 리뷰어가 변경 목적과 영향을 파악할 수 있는 수준으로 유지하는 방식을 권장합니다.

## 6. Code Review

- 리뷰어는 기능 요구사항, 예외 처리, 데이터 정합성, 보안, 테스트, API 호환성을 확인합니다.
- 수정 요청에는 코드 변경 또는 논의 결과로 응답합니다.
- 작성자는 변경 후 스스로 diff를 다시 확인하고 필요한 테스트를 재실행합니다.
- 필요한 승인 인원과 필수 검사 항목은 팀 규모와 GitHub 설정에 맞춰 별도로 합의합니다.

## 7. Merge

1. 합의된 리뷰와 검증이 끝난 뒤 `main`에 merge합니다.
2. merge 방식은 커밋 이력 정책에 따라 Squash, Rebase, Merge commit 중 팀이 결정합니다. 간결한 이력을 원한다면 Squash and merge를 기본안으로 고려할 수 있습니다.
3. merge 후 연결된 이슈가 닫혔는지 확인합니다.
4. 더 이상 사용하지 않는 작업 브랜치는 삭제하는 방식을 권장합니다.
5. merge된 최신 `main`을 로컬에 반영한 뒤 다음 작업을 시작합니다.

`main` 직접 push 제한, 필수 승인 수, 상태 검사와 같은 GitHub 저장소 설정은 이번 문서에서 정하지 않습니다.
